# Типы баз данных

Выбор правильного типа базы данных критически важен для производительности, масштабируемости и удобства разработки. Разные типы БД решают разные задачи и оптимизированы под различные паттерны использования.

Перед выбором продукта стоит ответить на четыре вопроса: какая **структура** данных, какие **запросы** нужны, насколько строгая **согласованность**, какой **масштаб** записи и чтения. Ниже — кратко про ACID и развилку «таблицы / документы / граф», затем обзор основных моделей.

---

## ACID

**ACID** — набор гарантий транзакции в классических СУБД:

* **Atomicity (атомарность)** — либо выполняются все шаги транзакции, либо ни один (нет «полуперевода»).
* **Consistency (согласованность)** — после коммита данные удовлетворяют ограничениям схемы (FK, CHECK, инварианты приложения).
* **Isolation (изоляция)** — параллельные транзакции не портят друг другу промежуточное состояние.
* **Durability (долговечность)** — после успешного commit данные не теряются при сбое (WAL, fsync и т.п.).

**Мини-пример.** Перевод денег: списать со счёта A и зачислить на B должно быть одной транзакцией. Если после списания упал сервер — откат, баланс не «завис» посередине. То же для заказа: заказ + позиции + списание склада — атомарно.

На собеседованиях ACID часто противопоставляют **BASE** (eventual consistency) и разбирают в связке с [CAP-теоремой](./cap-theorem.md). Здесь достаточно помнить: если критичны деньги, заказы, инвентарь — обычно начинают с реляционной БД с ACID.

## Быстрая развилка: SQL, MongoDB или граф

Одна и та же предметная область может жить в разных моделях. Ориентир:

| Задача | Лучше начать с | Почему |
|--------|----------------|--------|
| Заказы, оплата, инвентарь, отчёты с JOIN | **Табличная (PostgreSQL / MySQL)** | Схема, FK, строгий ACID, сложные запросы |
| CMS, каталог с разной формой документов, профили | **Документная (MongoDB)** | Гибкая схема, документ читается целиком, проще горизонтально расти |
| Friends-of-friends, fraud-цепочки, рекомендации по связям | **Графовая (Neo4j и др.)** | Обход рёбер на много hops без тяжёлых JOIN |

**Табличная (Postgres).** Заказ ссылается на пользователя и товары; нужны JOIN и транзакция «создать заказ + позиции + оплата». Это дефолт для OLTP с целостностью.

**Документная (Mongo).** Статья или товар с вложенными полями и вариациями структуры — один документ. Multi-document transactions в MongoDB есть (на replica set), но для сложной банковской логики и жёстких кросс-сущностных инвариантов обычно всё ещё выбирают SQL: модель и tooling привычнее, JOIN и constraints сильнее.

**Графовая (Neo4j).** «Друзья друзей», путь мошенничества через цепочку аккаунтов, knowledge graph. Если связей мало (1–2 hop), часто хватает SQL и recursive CTE / self-join. Граф оправдан, когда глубина обхода большая и связи — главный объект запросов.

Ниже — полный обзор типов; развилка выше помогает не теряться в деталях.

## Реляционные БД (SQL)

### Что это?

Реляционные базы данных хранят данные в виде таблиц (relations) со строгими связями между ними. Данные организованы в строки (records) и столбцы (attributes), а связи определяются через внешние ключи (foreign keys).

### Характеристики

* **ACID-транзакции**: атомарность, согласованность, изоляция, долговечность (см. [выше](#acid))
* **Схема данных**: Строгая структура, определённая заранее
* **SQL**: Стандартизированный язык запросов
* **Связи**: Поддержка JOIN-операций между таблицами
* **Целостность данных**: Ограничения (constraints), индексы, триггеры

### Примеры БД

* **PostgreSQL** — мощная open-source БД с расширенными возможностями
* **MySQL / MariaDB** — популярная БД для веб-приложений
* **SQL Server** — коммерческая БД от Microsoft
* **Oracle** — enterprise-решение для крупных систем
* **SQLite** — встраиваемая БД для небольших приложений

### Когда использовать?

* **Структурированные данные** с чёткими связями (пользователи → заказы → товары)
* **Требуются ACID-гарантии** (финансовые транзакции, заказы)
* **Сложные запросы** с JOIN и агрегациями
* **Важна целостность данных** (валидация, ограничения)
* **Средний/низкий объём данных** (до сотен ГБ на один сервер)

### Когда не использовать?

* **Очень большие объёмы данных** (петабайты) без шардирования
* **Горизонтальное масштабирование записи** (сложно без шардирования)
* **Гибкая схема данных** (часто меняющаяся структура)
* **Высокая нагрузка на запись** (миллионы записей в секунду)

### Примеры кейсов

#### Сервис доставки еды

**Почему реляционная БД?**
* Чёткая структура: пользователи, рестораны, заказы, блюда
* Требуется целостность данных (заказ должен ссылаться на существующего пользователя)
* Сложные запросы: "найти все заказы пользователя за последний месяц с деталями блюд"
* Транзакции: создание заказа должно быть атомарным (заказ + позиции + оплата)

**Структура**:
```sql
users (id, name, email, phone)
restaurants (id, name, address, city)
dishes (id, restaurant_id, name, price)
orders (id, user_id, restaurant_id, status, total)
order_items (id, order_id, dish_id, quantity)
```

#### Банковское приложение

**Почему реляционная БД?**
* Критична ACID-совместимость (перевод денег должен быть атомарным)
* Строгие требования к целостности данных
* Сложная аналитика и отчётность
* Аудит и соответствие регуляторным требованиям

#### E-commerce платформа

**Почему реляционная БД?**
* Связи между категориями, товарами, заказами, клиентами
* Сложные запросы для каталога (фильтры, сортировка, поиск)
* Управление инвентарём требует транзакций

## Документные БД (NoSQL)

### Что это?

Документные БД хранят данные в виде документов (обычно JSON/BSON). Каждый документ может иметь свою структуру, что обеспечивает гибкость схемы.

### Характеристики

* **Гибкая схема**: Каждый документ может иметь разные поля
* **Вложенные структуры**: Документы могут содержать массивы и объекты
* **Горизонтальное масштабирование**: Легче масштабировать, чем реляционные БД
* **Быстрые запросы**: Оптимизированы для чтения по ключу или индексу
* **Eventual consistency**: В некоторых конфигурациях возможна задержка согласованности

### Примеры БД

* **MongoDB** — самая популярная документная БД
* **CouchDB** — БД с репликацией и REST API
* **DynamoDB** — управляемая БД от AWS
* **Firestore** — БД от Google Cloud

### Когда использовать?

* **Гибкая/меняющаяся схема** (профили пользователей с разными полями)
* **Документо-ориентированные данные** (блоги, каталоги товаров, контент)
* **Быстрое прототипирование** (не нужно определять схему заранее)
* **Горизонтальное масштабирование** (большие объёмы данных)
* **Географически распределённые данные**

### Когда не использовать?

* **Сложные JOIN-запросы** (нужны реляционные связи)
* **Сложная кросс-документная бизнес-логика** (финансы, инвентарь) — multi-document transactions в MongoDB есть, но для строгих инвариантов и tooling обычно предпочтительнее SQL
* **Сложная аналитика** (агрегации по множеству документов)
* **Малые объёмы данных** (overhead не оправдан)

### Примеры кейсов

#### Система управления контентом (CMS)

**Почему документная БД?**
* Разные типы контента (статьи, видео, галереи) с разной структурой
* Вложенные структуры (статья → теги, категории, метаданные)
* Быстрое чтение по ID или slug
* Гибкость для добавления новых полей без миграций

**Пример документа**:
```json
{
  "_id": "article_123",
  "title": "Как выбрать БД",
  "content": "...",
  "author": {
    "id": "user_456",
    "name": "Иван Иванов"
  },
  "tags": ["database", "nosql"],
  "published_at": "2024-01-25T10:00:00Z",
  "metadata": {
    "views": 1500,
    "likes": 42
  }
}
```

#### Каталог товаров с вариациями

**Почему документная БД?**
* Товары имеют разную структуру (одежда: размер, цвет; электроника: характеристики)
* Вложенные данные (товар → варианты → цены → склады)
* Быстрый поиск по категориям и атрибутам

#### Профили пользователей в социальной сети

**Почему документная БД?**
* Разные пользователи имеют разные поля (профиль может быть минимальным или расширенным)
* Вложенные структуры (списки друзей, интересы, настройки)
* Горизонтальное масштабирование для миллионов пользователей

## БД типа "ключ-значение" (Key-Value)

### Что это?

Самый простой тип NoSQL БД. Хранит данные как пары ключ-значение. Значение может быть любой структурой (строка, число, JSON, бинарные данные).

### Характеристики

* **Простота**: Минимальная модель данных
* **Высокая производительность**: Оптимизированы для быстрого чтения/записи по ключу
* **Горизонтальное масштабирование**: Легко распределяются по кластеру
* **In-memory опции**: Могут хранить данные в RAM для максимальной скорости

### Примеры БД

* **Redis** — in-memory БД, часто используется как кэш
* **Memcached** — распределённый кэш в памяти
* **DynamoDB** — управляемая БД от AWS (также документная)
* **Riak** — распределённая БД ключ-значение
* **etcd** — распределённое хранилище конфигураций

### Когда использовать?

* **Кэширование** (сессии, результаты запросов, популярный контент)
* **Хранение сессий** (session storage)
* **Счётчики и очереди** (Redis lists, sets, sorted sets)
* **Временные данные** (TTL, временные токены)
* **Рейтинги и leaderboards** (Redis sorted sets)
* **Pub/Sub системы** (Redis pub/sub)

### Когда не использовать?

* **Сложные запросы** (нет JOIN, агрегаций)
* **Поиск по значениям** (только по ключу)
* **Связи между данными** (нет реляционных связей)
* **Долгосрочное хранение** (если in-memory, данные могут быть потеряны)

### Примеры кейсов

#### Кэширование результатов запросов

**Почему Redis?**
* Быстрый доступ к часто запрашиваемым данным
* Снижение нагрузки на основную БД
* TTL для автоматической инвалидации кэша

**Пример**:
```text
Ключ: "restaurant:123:menu"
Значение: JSON с меню ресторана
TTL: 1 час
```

#### Хранение сессий пользователей

**Почему Redis?**
* Быстрый доступ к сессиям
* Автоматическое удаление при истечении TTL
* Распределённое хранение для микросервисов

**Пример**:
```text
Ключ: "session:abc123xyz"
Значение: {"user_id": 456, "role": "customer", "cart": [...]}
TTL: 30 минут
```

#### Счётчик просмотров в реальном времени

**Почему Redis?**
* Атомарные операции (INCR)
* Высокая производительность записи
* Можно использовать для rate limiting

**Пример**:
```text
Ключ: "views:article:789"
Значение: 15234
Операция: INCR views:article:789
```

#### Очередь задач (Task Queue)

**Почему Redis?**
* Redis Lists для FIFO очередей
* Redis Pub/Sub для уведомлений
* Высокая пропускная способность

## Колоночные БД (Columnar)

### Что это?

Колоночные БД хранят данные по столбцам, а не по строкам. Это позволяет эффективно сжимать данные и быстро выполнять аналитические запросы.

### Характеристики

* **Сжатие данных**: Высокая степень сжатия за счёт однотипных данных в столбце
* **Аналитические запросы**: Оптимизированы для агрегаций и аналитики
* **Горизонтальное масштабирование**: Легко распределяются
* **Time-series данные**: Хорошо подходят для временных рядов

### Примеры БД

* **Cassandra** — распределённая колоночная БД
* **HBase** — колоночная БД на основе Hadoop
* **ClickHouse** — аналитическая БД для больших данных
* **Amazon Redshift** — управляемое хранилище данных

### Когда использовать?

* **Аналитика и BI** (агрегации, отчёты, дашборды)
* **Большие объёмы данных** (терабайты, петабайты)
* **Чтение преобладает над записью** (аналитические запросы)
* **Временные ряды** (метрики, логи, события)
* **Data warehousing** (хранилища данных)

### Когда не использовать?

* **OLTP-нагрузка** (много мелких транзакций)
* **Сложные JOIN-запросы** (не оптимизированы)
* **Частые обновления** (запись медленнее, чем в row-based БД)
* **Малые объёмы данных** (overhead не оправдан)

### Примеры кейсов

#### Аналитика пользовательского поведения

**Почему ClickHouse?**
* Миллиарды событий (клики, просмотры, покупки)
* Быстрые агрегации ("сколько пользователей из Москвы купили товар X за последний месяц")
* Высокая степень сжатия данных

**Пример запроса**:
```sql
SELECT 
  city,
  COUNT(*) as purchases,
  SUM(amount) as total_revenue
FROM events
WHERE event_type = 'purchase'
  AND date >= '2024-01-01'
GROUP BY city
ORDER BY total_revenue DESC
```

#### Хранилище логов (Log Warehouse)

**Почему колоночная БД?**
* Огромные объёмы логов (миллионы записей в день)
* Аналитические запросы ("найти все ошибки за последний час")
* Эффективное сжатие

#### Метрики и мониторинг

**Почему колоночная БД?**
* Временные ряды метрик (CPU, память, запросы)
* Быстрые агрегации для дашбордов
* Долгосрочное хранение исторических данных

## Графовые БД (Graph)

### Что это?

Графовые БД хранят данные в виде узлов (nodes) и рёбер (edges), представляющих связи между сущностями. Оптимизированы для запросов, связанных с отношениями и графами.

### Характеристики

* **Узлы и рёбра**: Данные представлены как граф
* **Свойства**: Узлы и рёбра могут иметь свойства
* **Графовые запросы**: Оптимизированы для обхода графа
* **Сложные связи**: Эффективная работа с многоуровневыми связями

### Примеры БД

* **Neo4j** — самая популярная графовая БД
* **Amazon Neptune** — управляемая графовая БД от AWS
* **ArangoDB** — мультимодельная БД (документная + графовая)
* **JanusGraph** — распределённая графовая БД

### Когда использовать?

* **Социальные сети** (друзья, подписчики, рекомендации)
* **Рекомендательные системы** ("люди, которые купили X, также купили Y")
* **Fraud detection** (обнаружение мошеннических схем)
* **Knowledge graphs** (базы знаний, онтологии)
* **Маршрутизация** (поиск путей, навигация)
* **Анализ связей** (кто с кем связан, влияние)

### Когда не использовать?

* **Простые структуры данных** (overhead не оправдан)
* **Аналитические запросы** (агрегации по большим объёмам)
* **Высокая нагрузка на запись** (обновление графа может быть медленным)
* **Малые объёмы данных / мало hops** (1–2 уровня связей часто закрываются SQL и CTE)

### Примеры кейсов

#### Социальная сеть

**Почему Neo4j?**
* Быстрый поиск друзей друзей (2-3 уровня связей)
* Рекомендации друзей ("друзья твоих друзей")
* Поиск кратчайшего пути между пользователями

**Пример запроса**:
```cypher
// Найти друзей друзей пользователя 123
MATCH (user:User {id: 123})-[:FRIENDS]->(friend)-[:FRIENDS]->(friendOfFriend)
WHERE NOT (user)-[:FRIENDS]->(friendOfFriend)
RETURN friendOfFriend
```

#### Рекомендательная система для e-commerce

**Почему графовая БД?**
* Связи между товарами (совместные покупки)
* Рекомендации на основе графа покупок
* Поиск похожих товаров через связи

**Структура**:
```
(Пользователь)-[КУПИЛ]->(Товар A)
(Товар A)-[СОВМЕСТНО_С]->(Товар B)
→ Рекомендовать Товар B пользователю
```

#### Обнаружение мошенничества

**Почему графовая БД?**
* Поиск подозрительных связей между аккаунтами
* Обнаружение схем (аккаунт A → транзакция → аккаунт B → транзакция → аккаунт C)
* Анализ паттернов мошенничества

## БД временных рядов (Time-Series)

### Что это?

Специализированные БД для хранения данных, которые изменяются во времени. Оптимизированы для записи и чтения временных рядов (метрики, события, сенсорные данные).

### Характеристики

* **Временные метки**: Данные привязаны к времени
* **Высокая скорость записи**: Оптимизированы для потоковой записи
* **Сжатие данных**: Эффективное сжатие временных рядов
* **Агрегации по времени**: Быстрые запросы по временным интервалам
* **TTL и retention**: Автоматическое удаление старых данных

### Примеры БД

* **InfluxDB** — популярная TSDB
* **TimescaleDB** — расширение PostgreSQL для временных рядов
* **Prometheus** — мониторинг и метрики
* **OpenTSDB** — распределённая TSDB
* **Amazon Timestream** — управляемая TSDB от AWS

### Когда использовать?

* **Мониторинг и метрики** (CPU, память, сеть, приложения)
* **IoT и сенсоры** (температура, давление, GPS-координаты)
* **Финансовые данные** (котировки, транзакции)
* **Аналитика событий** (логи, события пользователей)
* **Трекинг в реальном времени** (позиции курьеров, транспорт)

### Когда не использовать?

* **Неструктурированные данные** без временной привязки
* **Сложные JOIN-запросы** (нет реляционных связей)
* **Редкие запросы** (overhead не оправдан)
* **Данные без временной компоненты**

### Примеры кейсов

#### Мониторинг инфраструктуры

**Почему InfluxDB?**
* Метрики серверов (CPU, RAM, диск) каждые 10 секунд
* Быстрые запросы для дашбордов ("CPU за последний час")
* Автоматическое удаление данных старше 90 дней

**Пример данных**:
```text
measurement: cpu_usage
tags: server=web-01, datacenter=moscow
fields: usage=45.2
timestamp: 2024-01-25T10:30:00Z
```

#### Трекинг курьеров в реальном времени

**Почему TimescaleDB?**
* GPS-координаты курьеров каждые 5-10 секунд
* Быстрые запросы ("где находится курьер заказа 123?")
* Геопространственные запросы (PostGIS)

#### Финансовые котировки

**Почему TSDB?**
* Котировки акций каждую секунду
* Агрегации ("средняя цена за час", "максимум за день")
* Исторические данные для анализа

## Файловые хранилища

### Что это?

Хранение данных в виде файлов в файловой системе. Не является БД в классическом понимании, но часто используется для хранения больших объёмов неструктурированных данных.

### Характеристики

* **Простота**: Прямой доступ к файлам
* **Большие файлы**: Оптимизированы для хранения медиа
* **Объектное хранилище**: S3-подобные системы
* **Масштабирование**: Легко масштабируются горизонтально

### Примеры систем

* **Amazon S3** — объектное хранилище
* **Google Cloud Storage** — облачное хранилище
* **Azure Blob Storage** — хранилище от Microsoft
* **MinIO** — open-source S3-совместимое хранилище
* **HDFS** — распределённая файловая система Hadoop

### Когда использовать?

* **Медиа-файлы** (изображения, видео, аудио)
* **Архивы и бэкапы** (логи, дампы БД)
* **Статический контент** (CDN, веб-сайты)
* **Большие файлы** (датасеты для ML, видео)
* **Долгосрочное хранение** (холодное хранилище)

### Когда не использовать?

* **Структурированные данные** (используй БД)
* **Быстрый поиск** (нет индексов)
* **Транзакции** (нет ACID)
* **Сложные запросы** (только чтение файлов)

### Примеры кейсов

#### Хранение изображений товаров

**Почему S3?**
* Миллионы изображений товаров
* CDN для быстрой доставки
* Масштабируемость и надёжность
* Низкая стоимость хранения

#### Бэкапы баз данных

**Почему объектное хранилище?**
* Ежедневные дампы БД
* Долгосрочное хранение (месяцы, годы)
* Низкая стоимость холодного хранилища
* Восстановление при необходимости

#### Хранилище видео-контента

**Почему объектное хранилище?**
* Большие файлы (видео могут быть гигабайтами)
* Потоковая доставка через CDN
* Масштабируемость для миллионов видео

## Сравнительная таблица

| Тип БД | Лучше для | Худше для | Примеры |
|--------|-----------|-----------|---------|
| **Реляционная** | Структурированные данные, ACID, сложные запросы | Горизонтальное масштабирование записи, гибкая схема | PostgreSQL, MySQL |
| **Документная** | Гибкая схема, горизонтальное масштабирование | Сложные JOIN, жёсткая кросс-документная логика | MongoDB, CouchDB |
| **Ключ-значение** | Кэширование, сессии, простые структуры | Сложные запросы, связи | Redis, Memcached |
| **Колоночная** | Аналитика, большие объёмы, чтение | OLTP, частые обновления | Cassandra, ClickHouse |
| **Графовая** | Связи, рекомендации, социальные сети | Простые структуры, аналитика | Neo4j, Neptune |
| **Временные ряды** | Метрики, IoT, мониторинг | Неструктурированные данные | InfluxDB, TimescaleDB |
| **Файловое** | Медиа, архивы, большие файлы | Структурированные данные, поиск | S3, GCS |

## Как выбрать БД

### Вопросы для принятия решения

1. **Какая структура данных?** (структурированная → реляционная, гибкая → документная)
2. **Какие требования к согласованности?** (строгие → реляционная, eventual → NoSQL)
3. **Какой объём данных?** (малый → реляционная, огромный → колоночная/NoSQL)
4. **Какая нагрузка?** (OLTP → реляционная, аналитика → колоночная)
5. **Нужны ли связи?** (сложные многоуровневые → графовая, простые → реляционная)
6. **Временные данные?** (метрики, события → TSDB)
7. **Нужен ли кэш?** (Redis, Memcached)

### Типичные комбинации

* **Реляционная БД + Redis** — основное хранилище + кэш
* **MongoDB + Elasticsearch** — документы + полнотекстовый поиск
* **PostgreSQL + TimescaleDB** — OLTP + временные ряды
* **Cassandra + Spark** — большие данные + аналитика
