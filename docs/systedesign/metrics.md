# Метрики и мониторинг

Метрики — это числовые измерения состояния системы во времени. Они отвечают на вопросы «насколько быстро», «сколько нагрузки», «сколько ошибок» и «не упираемся ли в ресурсы». Без них невозможно выполнить [нефункциональные требования](./functional-and-non-functional-requirements.md) (latency, throughput, availability) и принять решение о [масштабировании](./scaling.md).

**Метрики vs логи:**
* **Метрики** — агрегированные числа (RPS, p95 latency, CPU %). Дешёвые в хранении, удобны для графиков и алертов.
* **Логи** — отдельные события с контекстом (stack trace, user_id). Нужны для расследования инцидента, но плохо подходят для «тренда за месяц».

На практике используют оба: метрика срабатывает алерт → логи помогают найти причину.

---

## 🔹 Типы метрик (Prometheus-модель)

| Тип | Что измеряет | Примеры |
|-----|--------------|---------|
| **Counter** | Только растёт (сбрасывается при рестарте) | `http_requests_total`, `errors_total` |
| **Gauge** | Текущее значение в момент времени | CPU %, длина очереди, число активных соединений |
| **Histogram** | Распределение значений по «корзинам» | Время ответа API → из него считают p50, p95, p99 |

Для **latency** почти всегда нужен **histogram** (или summary), а не среднее по counter — иначе вы не увидите «хвост» медленных запросов.

---

## 🔹 Latency (задержка)

### Что это

**Latency** — время от начала запроса до получения ответа. Обычно измеряется в **миллисекундах (мс)**.

### Что именно измерять

| Уровень | Что включает | Когда смотреть |
|---------|--------------|----------------|
| **End-to-end** | Клиент → сеть → CDN → LB → API → БД → обратно | UX, SLA перед пользователем |
| **Server time** | Только обработка на сервере (без сети клиента) | Оптимизация кода и БД |
| **Upstream** | Время вызова БД, кэша, другого сервиса | Поиск узкого места |

Один и тот же API может иметь server time 50 мс и end-to-end 300 мс из-за мобильной сети — это разные метрики.

### Где снимать

```text
Клиент / CDN  →  Load Balancer  →  API-сервис  →  Кэш / БД / Очередь
     ↑                ↑                ↑                  ↑
  Real User      access log        middleware         query time
  Monitoring     (nginx/envoy)     (trace span)       (pg_stat, redis)
```

* **Load balancer** — первая точка после входа в ваш периметр.
* **APM / tracing** (OpenTelemetry, Jaeger) — разбивка latency по span внутри запроса.
* **БД** — `query duration`, slow query log.

### Почему не среднее (average)

Средняя latency **скрывает выбросы**. Пример: 990 запросов по 50 мс и 10 запросов по 5 000 мс → среднее ≈ 99 мс, хотя 1% пользователей ждут 5 секунд. Для NFR и алертов используют **перцентили**.

---

## 🔹 Перцентили: p50, p95, p99

### Определение

**p95 = 200 мс** означает: **95% запросов** обработаны быстрее 200 мс, **5%** — медленнее или равны 200 мс.

| Перцентиль | Другое имя | Когда смотреть |
|------------|------------|----------------|
| **p50** | медиана | «Типичный» пользователь |
| **p95** | — | Стандарт для NFR и алертов на API |
| **p99** | — | «Хвост», редкие, но болезненные случаи (тяжёлые запросы, GC, cold cache) |
| **p999** | — | Крупные системы, где даже 0.1% — тысячи пользователей |

### Интуиция

При **1 000 RPS** один процент медленных запросов — это **10 req/s** с плохим опытом. Средняя latency может выглядеть нормально, а **p99** покажет проблему.

### Типичные NFR на собеседовании

* «p95 API < 200 мс при пиковой нагрузке»
* «p99 поиска < 500 мс»
* «p50 страницы ленты < 100 мс»

Уточняйте: **какой endpoint**, **read или write**, **с кэшем или без**.

---

## 🔹 RPS, throughput, QPS

### Что это

* **RPS** (Requests Per Second) — HTTP-запросов в секунду к API.
* **QPS** (Queries Per Second) — часто то же для БД или поиска.
* **Throughput** — пропускная способность: запросы/с, сообщения/с, МБ/с.

Термины часто используют как синонимы для внешнего трафика; важно явно указывать **уровень** (внешний API vs внутренние вызовы к БД).

### Связь с оценкой нагрузки

Расчёт пикового RPS из DAU — в статье [Оценка нагрузки и ресурсов](./load-estimation.md). Кратко:

1. Запросы в день → средний RPS = запросы / 86 400.
2. Умножить на коэффициент пика (×3–×5 для обеда/вечера).
3. Разделить на **read / write** (часто 90% / 10%).

**Важно:** 25 RPS на API может давать **100–200 RPS** к БД и кэшу из-за внутренних вызовов — это разные метрики.

### Когда RPS растёт, а latency стабильна

Система масштабируется линейно. Когда latency растёт при том же RPS — узкое место (БД, lock, исчерпан пул соединений).

---

## 🔹 Error rate (доля ошибок)

### Что считать ошибкой

* HTTP **5xx** — ошибка сервера.
* **4xx** — обычно ошибка клиента (не всегда алертят).
* **Таймауты** — клиент не дождался ответа (часто хуже 500 для UX).
* Ошибки воркеров очередей, failed jobs.

**Error rate** = (число ошибок / число запросов) × 100%.

Пример: 0.1% при 10 000 RPS = **10 ошибок в секунду** — это много для критичного checkout.

### Связь с availability

**Availability** ≈ 1 − error_rate (упрощённо). SLA «99.9% uptime» допускает ~43 минуты простоя в месяц — метрики показывают, не «съедаете» ли вы бюджет одним инцидентом.

---

## 🔹 Saturation (насыщение ресурсов)

Показывает, **насколько близко система к пределу**. Рост saturation при стабильном RPS — сигнал «скоро деградация».

| Метрика | Зачем | Ориентир «насторожиться» |
|---------|-------|---------------------------|
| **CPU** | Вычисления, JSON, сериализация | Устойчиво > 70–80% |
| **RAM** | Кэш в памяти, утечки | > 85%, OOM kill |
| **Disk I/O** | БД, логи | Высокий iowait, очередь диска |
| **Connection pool** | Исчерпание соединений к БД | Ожидание в очереди, timeout |
| **Queue length / lag** | Очереди, Kafka | Рост без отката — см. [Message Queues](./message-queues.md) |
| **Network** | Исходящий трафик, лимиты | Bandwidth near cap |

Когда saturation высокая **и** растут p95 или error rate — пора [масштабировать](./scaling.md) или оптимизировать узкое место.

---

## 🔹 Cache hit rate

**Cache hit rate** = (запросы, ответившие из кэша) / (все запросы к данным) × 100%.

* Высокий hit rate → меньше нагрузка на БД, ниже latency.
* Падение hit rate после деплоя → возможно, сброс кэша или смена ключей.

Подробнее о стратегиях — [Стратегии кэширования](./caching-strategies.md).

---

## 🔹 Golden Signals (Google SRE)

Четыре сигнала, с которых начинают любой дашборд сервиса:

| Сигнал | Метрики | Вопрос |
|--------|---------|--------|
| **Latency** | p50, p95, p99 по endpoint | Насколько быстро? |
| **Traffic** | RPS, bytes/s | Сколько нагрузки? |
| **Errors** | 5xx rate, timeout rate | Сколько сбоев? |
| **Saturation** | CPU, RAM, pool, queue lag | Есть ли запас? |

Если на собеседовании просят «как мониторить сервис» — перечислите Golden Signals и один инструмент сбора.

---

## 🔹 SLA, SLO, SLI

| Термин | Кто задаёт | Пример |
|--------|------------|--------|
| **SLA** | Договор с клиентом / бизнесом | «Доступность 99.9% в месяц» |
| **SLO** | Внутренняя цель команды | «p95 search API < 300 мс» |
| **SLI** | Конкретное измерение для SLO | «Доля запросов search с latency < 300 мс» |

**Пример SLO:** 99.9% запросов `GET /api/questions` за 28 дней имеют latency < 200 мс (измерение по histogram на ingress).

**Error budget:** если SLO на доступность 99.9%, «бюджет» простоя ~43 мин/мес. Тратишь его на релизы и риск — или замораживаешь деплои.

NFR из требований («не более 500 мс при 10 000 RPS») — это кандидаты в **SLO**, их нужно привязать к **конкретным SLI** и дашбордам.

---

## 🔹 Где собирать метрики

| Задача | Инструменты | Комментарий |
|--------|-------------|-------------|
| Метрики инфраструктуры и сервисов | **Prometheus** + **Grafana** | Pull-модель, PromQL, стандарт в Kubernetes |
| Трейсы и разбор latency по слоям | **OpenTelemetry**, Jaeger, Tempo | Distributed tracing |
| APM «из коробки» | Datadog, New Relic, AppDynamics | Меньше возни, платно |
| Логи и поиск по событиям | **ELK Stack** | Не заменяет метрики; см. [Стек ELK](./elk-stack.md) |
| Алерты on-call | PagerDuty, Opsgenie, Grafana Alerting | По SLO, не по «среднему CPU» без контекста |

**Практика:** приложение экспортирует histogram latency и counter RPS → Prometheus скрейпит → Grafana дашборд → алерт на p95 и error rate.

## 🔹 Дашборды и алерты

### Performance Dashboard

* RPS по endpoint и методу (GET/POST)
* Latency: **p50, p95, p99** (не только average)
* Error rate (5xx, timeouts)
* Сравнение с прошлой неделей (регрессии после релиза)

### Infrastructure Dashboard

* CPU, RAM, disk по нодам / подам
* Database connections, replication lag
* Cache hit rate
* Queue length / consumer lag

### На что алертить

| Хорошо | Плохо |
|--------|-------|
| p95 latency > SLO 5 минут | Средняя CPU > 50% без контекста |
| Error rate > 1% | Любой единичный 500 |
| Queue lag > порога | RPS упал на 1% (часто шум) |
| SLO burn rate (быстрое «сжигание» бюджета) | Алерт без runbook |

У каждого алерта должен быть **runbook**: что проверить (дашборд, логи, последний деплой).

## 📝 На собеседовании

**1. «Какие метрики вы бы мониторили для API?»**

→ Golden Signals: p95 latency по endpoint, RPS, 5xx rate, CPU/RAM/pool saturation. Плюс бизнес-метрики при необходимости.

**2. «Почему p95, а не среднее?»**

→ Среднее скрывает хвост; p95 отражает опыт большинства и совпадает с типичными NFR.

**3. «RPS 1000 — выдержит один сервер?»**

→ Зависит от работы на запрос (CPU, N+1 к БД). Смотрите saturation и p95 под нагрузкой, не только RPS. См. [Оценка нагрузки](./load-estimation.md).

**4. «Как связаны метрики и масштабирование?»**

→ Масштабируем, когда p95/error rate деградируют при росте traffic или saturation стабильно высокая.

**5. «Чем метрики отличаются от логов?»**

→ Метрики — тренд и алерт; логи — детали инцидента. Вместе: алерт по p95 → trace/log → root cause.
