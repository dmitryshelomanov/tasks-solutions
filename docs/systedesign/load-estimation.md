# Оценка нагрузки и ресурсов

При проектировании системы критически важно правильно оценить нагрузку, объём данных и необходимые ресурсы (CPU, RAM, диск). Это позволяет выбрать правильную архитектуру и избежать проблем с производительностью на ранних этапах.

---

## 🔹 Шаг 1. Оценка нагрузки: сколько запросов в секунду (RPS)?

Что такое RPS, QPS и throughput в мониторинге — см. [Метрики и мониторинг → RPS](./metrics.md#rps-throughput-qps).

### Исходные данные

Для примера рассмотрим сервис доставки еды:
* 100 000 активных пользователей в день
* Средний пользователь делает 5 запросов в сессию (открыть приложение → поиск → меню → заказ → отслеживание)
* Пиковая нагрузка — в 4 раза выше средней (обед/ужин в Москве)

### Расчёт

1. **Общее число запросов в день**:  
   100 000 пользователей × 5 = 500 000 запросов/день

2. **Среднее RPS**:  
   500 000 / (24 × 3600) ≈ 5.8 RPS

3. **Пиковое RPS (с запасом)**:  
   5.8 × 4 ≈ 25 RPS

✅ Это внешние HTTP-запросы к API. Но внутри будут десятки внутренних вызовов (к БД, кэшу и т.д.).

---

## 🔹 Шаг 2. Понять: чтение или запись в БД?

### Метод: проанализировать пользовательские сценарии

| Действие пользователя | Тип запроса к БД | Пример |
|----------------------|------------------|--------|
| Открыть список ресторанов | Чтение | `SELECT * FROM restaurants WHERE city = 'Москва'` |
| Посмотреть меню | Чтение | `SELECT * FROM dishes WHERE restaurant_id = 123` |
| Оформить заказ | Запись | `INSERT INTO orders (...) + обновление статуса` |
| Отследить курьера | Чтение (иногда + запись координат курьера) | `SELECT courier_lat, lon FROM deliveries WHERE order_id = ...` |

### Грубое распределение

* **90% — чтение**
* **10% — запись**

Это типично для большинства веб-приложений (особенно e-commerce, delivery, media).

### Как проверить в реальности?

* **В продакшене**: логи запросов, APM-системы (Datadog, New Relic), slow query log
* **На этапе проектирования**: считай по user journey

⚠️ Если у тебя много IoT/трекинга (курьеры шлют координаты каждые 5 сек), то записей может быть больше!

## 🔹 Шаг 3. Оценка дискового пространства

### Что хранится в БД?

Допустим, у нас есть таблицы:
* `users` (100K записей)
* `restaurants` (10K)
* `dishes` (500K)
* `orders` (100K в день → 3.65M в год)
* `order_items`, `reviews`, `courier_locations` (доп. данные)

### Пример: таблица `orders`

| Поле | Тип | Размер (байт) |
|------|-----|---------------|
| `id` | BIGINT | 8 |
| `user_id` | INT | 4 |
| `restaurant_id` | INT | 4 |
| `status` | VARCHAR(20) | ~20 |
| `delivery_address` | TEXT | ~100 |
| `created_at` | TIMESTAMP | 8 |
| **Итого на запись** | | **~150 байт** |

На практике с учётом индексов, overhead СУБД — умножай на 2–3× → **~300–400 байт/запись**.

### Годовой объём `orders`

* 100 000 заказов/день × 365 = 36.5 млн заказов/год
* 36.5 млн × 400 байт ≈ **14.6 ГБ/год**

### Другие таблицы

* `users`: 100K × 500 байт ≈ **50 МБ**
* `dishes`: 500K × 300 байт ≈ **150 МБ**
* `courier_locations` (если курьеры шлют каждые 10 сек, 1000 курьеров):  
  1000 × 6 × 3600 × 24 = 51.8 млн записей/день → это уже терабайты!  
  → но такие данные часто хранят не в OLTP, а в TSDB (TimescaleDB, ClickHouse) или удаляют через TTL

### Итого

* **OLTP-БД (PostgreSQL)**: ~20–50 ГБ/год — легко помещается на одном диске
* Если есть трекинг в реальном времени — выноси геоданные в отдельное хранилище

✅ **Правило**: оцените "тяжёлые" сущности (логи, медиа, координаты) — они съедают 90% места.

## 🔹 Шаг 4. Оценка CPU и RAM

### Подход

1. **Один сервер может обрабатывать ~1000 RPS** (stateless, простые запросы, в облаке)
   * Реалистично: 300–1000 RPS на ядро, если нет тяжёлых вычислений
2. У тебя пик — 25 RPS на API → внутренних запросов к БД может быть 100–200 RPS
3. Современный сервер (4 ядра, 8–16 ГБ RAM) легко справляется с 5–10K RPS к БД, если есть кэш и индексы

### RAM

* PostgreSQL использует RAM для кэширования (`shared_buffers`, OS cache)
* **Правило**: RAM ≥ объём "горячих" данных
  * Если 80% запросов — к ресторанам Москвы (1K ресторанов × 100 блюд = 100K строк), это <100 МБ → 4 ГБ RAM более чем достаточно

### CPU

* Запись дороже чтения (особенно с индексами)
* Если у тебя 20 записей/сек — это ничего для современного CPU

✅ **Вывод**: для 100K DAU тебе не нужны кластеры БД — хватит одного мощного сервера + реплики.

## 🔹 Шаг 5. Когда пора масштабировать?

| Показатель | Порог для беспокойства |
|------------|------------------------|
| CPU | >70% постоянно |
| RAM | swap активно используется |
| Диск | >80% заполнения ИЛИ высокий I/O wait |
| Latency БД | >100 мс для чтения, >200 мс для записи |
| Replication lag | >5 сек |

---

## 📌 Итог: пошаговый чек-лист для оценки

1. **Оцени суточную активность** → переведи в пиковое RPS
2. **Раздели запросы на чтение/запись** (обычно 90/10)
3. **Оцени объём данных в год**:
   * Посчитай размер одной записи
   * Умножь на количество записей
   * Добавь 2× на индексы и overhead
4. **Оцени memory footprint**:
   * Горячие данные должны помещаться в RAM
5. **Выбери тип масштабирования**:
   * Если много чтений → репликация
   * Если много записей/данных → шардирование или архивация
6. **Не забудь про кэш (Redis)** — он снизит нагрузку на БД в 10–100 раз

## 💡 Пример вывода на собеседовании

> «При 100K активных пользователей в день мы ожидаем пиковую нагрузку около 25 RPS на API. Поскольку 90% операций — чтение (просмотр ресторанов и меню), мы начнём с одного PostgreSQL-сервера и двух read-реплик. Объём данных — порядка 20 ГБ в год, что легко помещается на SSD. RAM в 8 ГБ достаточно, чтобы кэшировать популярные рестораны Москвы. Если нагрузка вырастет в 10 раз — добавим шардирование по городам и вынесем трекинг курьеров в отдельную TSDB.»
