# CAP теорема и консистентность данных

CAP теорема (теорема Брюера) — это фундаментальный принцип в распределённых системах, который описывает компромиссы между тремя важными свойствами системы.

---

## 🔹 CAP теорема

### Что это?

CAP теорема утверждает, что в распределённой системе невозможно одновременно обеспечить все три свойства:

* **C**onsistency (Консистентность) — все узлы видят одни и те же данные одновременно
* **A**vailability (Доступность) — система остаётся доступной для чтения и записи
* **P**artition tolerance (Устойчивость к разделению) — система продолжает работать при сетевых сбоях

**Вывод**: можно гарантировать максимум 2 из 3 свойств одновременно.

### Визуализация

```text
        Consistency
           /\
          /  \
         /    \
        /      \
       /        \
Availability ──── Partition Tolerance
```

---

## 🔹 Три варианта выбора

### 1. CP (Консистентность + Устойчивость к разделению)

**Жертвуем**: Доступностью

**Характеристики**:
* Все узлы всегда видят одни и те же данные
* При разделении сети система блокирует запись до восстановления связи
* Гарантируется строгая консистентность

**Примеры**:
* **PostgreSQL** (с синхронной репликацией)
* **MongoDB** (с write concern majority)
* **HBase**
* **Zookeeper**

**Когда использовать**:
* Финансовые системы (банки, платежи)
* Системы, где консистентность критична
* Когда можно позволить временную недоступность

### 2. AP (Доступность + Устойчивость к разделению)

**Жертвуем**: Консистентностью

**Характеристики**:
* Система всегда доступна для чтения и записи
* При разделении сети разные узлы могут иметь разные данные
* Eventual consistency (в конечном счёте данные согласуются)

**Примеры**:
* **Cassandra**
* **DynamoDB**
* **CouchDB**
* **Riak**

**Когда использовать**:
* Системы с высокой нагрузкой на чтение
* Когда можно допустить временную несогласованность
* Социальные сети, рекомендательные системы
* Системы, где доступность важнее строгой консистентности

### 3. CA (Консистентность + Доступность)

**Жертвуем**: Устойчивостью к разделению

**Характеристики**:
* Строгая консистентность
* Высокая доступность
* НО: не работает при разделении сети (практически невозможно в распределённых системах)

**Примеры**:
* **Традиционные реляционные БД** (PostgreSQL, MySQL) на одном сервере
* **SQLite** (не распределённая)

**Когда использовать**:
* Монолитные системы на одном сервере
* Системы, где нет распределённости
* Не подходит для современных облачных систем

⚠️ **Важно**: В реальных распределённых системах (облако, несколько дата-центров) **Partition Tolerance обязательна**, поэтому выбор обычно между CP и AP.

## 🔹 Уровни консистентности

### 1. Строгая консистентность (Strong Consistency)

Все узлы видят одни и те же данные в любой момент времени.

**Пример**:
```sql
-- Транзакция в PostgreSQL
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- Все узлы видят изменения сразу после COMMIT
```

**Плюсы**:
* Простота понимания
* Гарантия актуальности данных

**Минусы**:
* Высокая latency (нужно ждать подтверждения от всех узлов)
* Меньшая доступность

### 2. Eventual Consistency (В конечном счёте консистентность)

Данные в конечном счёте согласуются, но не обязательно сразу.

**Пример**:

```text
Пользователь A в Москве → обновляет профиль
Пользователь B в Нью-Йорке → может увидеть старое значение
Через несколько секунд → оба видят новое значение
```

**Плюсы**:
* Высокая доступность
* Низкая latency
* Масштабируемость

**Минусы**:
* Возможны временные несоответствия
* Сложнее программировать

### 3. Слабая консистентность (Weak Consistency)

Нет гарантий, когда данные согласуются.

**Пример**: DNS-кэш, некоторые кэши

## 🔹 ACID vs BASE

### ACID (для строгой консистентности)

* **A**tomicity (Атомарность) — транзакция выполняется полностью или не выполняется
* **C**onsistency (Консистентность) — данные всегда в валидном состоянии
* **I**solation (Изоляция) — транзакции не мешают друг другу
* **D**urability (Долговечность) — изменения сохраняются после завершения

**Используется в**: PostgreSQL, MySQL, Oracle

### BASE (для eventual consistency)

* **B**asically **A**vailable — система доступна большую часть времени
* **S**oft state — состояние может изменяться без новых входных данных
* **E**ventually consistent — данные согласуются в конечном счёте

**Используется в**: Cassandra, DynamoDB, MongoDB (в некоторых режимах)

## 🔹 Практические примеры

### Пример 1: Банковское приложение

**Требования**: Строгая консистентность критична

**Выбор**: **CP система** (PostgreSQL с синхронной репликацией)

**Почему**:
* Перевод денег должен быть атомарным
* Нельзя допустить, чтобы два узла видели разные балансы
* Временная недоступность лучше, чем потеря денег

### Пример 2: Социальная сеть (лайки, комментарии)

**Требования**: Высокая доступность, можно допустить задержку в несколько секунд

**Выбор**: **AP система** (Cassandra, DynamoDB)

**Почему**:
* Если лайк появится через 2 секунды — это приемлемо
* Важнее, чтобы система была доступна
* Eventual consistency достаточна

### Пример 3: Система рекомендаций

**Требования**: Высокая нагрузка, можно допустить задержку

**Выбор**: **AP система** (DynamoDB, Redis с репликацией)

**Почему**:
* Рекомендации могут обновляться асинхронно
* Важнее скорость ответа, чем мгновенная актуальность

## 🔹 Компромиссы в реальных системах

### Гибридный подход

Многие системы используют **гибридный подход**:

1. **Критичные данные** → CP система (PostgreSQL)
   * Заказы, платежи, балансы

2. **Некритичные данные** → AP система (Cassandra, Redis)
   * Лайки, просмотры, метрики

3. **Кэш** → AP система (Redis)
   * Временная несогласованность допустима

### Пример архитектуры

```text
┌─────────────────┐
│   API Gateway   │
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
    ↓         ↓
┌────────┐ ┌──────────┐
│PostgreSQL│ │  Redis   │
│  (CP)   │ │   (AP)   │
│Заказы,  │ │Кэш, сессии│
│платежи  │ │          │
└────────┘ └──────────┘
```

## 💡 На собеседовании

**Вопрос**: "Как вы обеспечиваете консистентность в распределённой системе?"

**Хороший ответ**:
> "Мы используем гибридный подход. Для критичных данных (заказы, платежи) — PostgreSQL с синхронной репликацией (CP, строгая консистентность). Для некритичных данных (лайки, просмотры) — Cassandra (AP, eventual consistency). Кэш в Redis также eventual consistent, но это приемлемо для наших use cases. Мы выбираем баланс между консистентностью и производительностью в зависимости от критичности данных."
