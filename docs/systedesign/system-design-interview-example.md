Этот документ демонстрирует пошаговый подход к решению задачи системного дизайна на примере сервиса поиска ответов (аналог Stack Overflow).

1. **Компоненты системы** — API, БД, кэш, CDN

## 🎯 Пример: Сервис поиска ответов

### Задача

Спроектировать сервис поиска ответов (простой Stack Overflow):
* Страница списка вопросов
* Страница ответа на вопрос с комментариями
* Можно выбрать правильный ответ
* Нужен SEO
* Нет авторизации и усложнений
* Список вопросов грузится долго, но страницу нужно показать быстро
* Ответ тоже может грузиться долго

---

## Шаг 1: Сбор требований

### Функциональные требования

✅ **Что система должна делать:**

1. **Список вопросов**
   * Отображение списка вопросов с заголовком, автором, датой, количеством ответов
   * Сортировка (по дате, популярности, количеству ответов)
   * Пагинация

2. **Страница вопроса**
   * Отображение вопроса с полным текстом
   * Список ответов к вопросу
   * Возможность отметить ответ как правильный
   * Комментарии к вопросу и ответам

3. **SEO**
   * SEO-friendly URLs
   * Мета-теги для поисковых систем
   * Server-Side Rendering (SSR) для индексации

### Нефункциональные требования

✅ **Как система должна работать:**

**Уточняющие вопросы интервьюеру:**

> **Q: Какая ожидаемая нагрузка?**  
> A: 10 млн пользователей в месяц, 100K активных пользователей в день

> **Q: Какое распределение чтение/запись?**  
> A: 95% чтение, 5% запись (типично для контентных систем)

> **Q: Какие требования к latency?**  
> A: Страница должна отображаться быстро (< 200 мс для первого байта), но контент может подгружаться асинхронно

> **Q: Нужна ли доступность 24/7?**  
> A: Да, 99.9% uptime

**Итоговые NFR:**

* **Производительность**: 
  * Первый байт (TTFB) < 200 мс
  * Полная загрузка страницы < 2 сек
  * Контент может подгружаться асинхронно

* **Масштабируемость**: 
  * Поддержка роста до 100 млн вопросов
  * Горизонтальное масштабирование

* **Доступность**: 
  * 99.9% uptime
  * Отказоустойчивость (реплики)

* **SEO**: 
  * Server-Side Rendering
  * SEO-friendly URLs

## Шаг 2: Оценка масштаба

### Расчёт нагрузки

**Исходные данные:**
* 10 млн пользователей в месяц
* 100K активных пользователей в день
* Средний пользователь делает 10 запросов в день

**Расчёт:**

1. **Запросов в день**: 100K × 10 = 1 млн запросов/день
2. **Среднее RPS**: 1 млн / (24 × 3600) ≈ 11.6 RPS
3. **Пиковое RPS** (с запасом ×5): 11.6 × 5 ≈ **60 RPS**

**Распределение:**
* **95% чтение** (список вопросов, страница вопроса) → ~57 RPS
* **5% запись** (новые вопросы, ответы, комментарии) → ~3 RPS

### Оценка объёма данных

**Структура данных:**

* **Вопрос**:
  * ID: 8 байт
  * Заголовок: ~100 байт
  * Текст: ~5 КБ
  * Автор, дата, метаданные: ~100 байт
  * **Итого**: ~5.2 КБ на вопрос

* **Ответ**:
  * ID: 8 байт
  * Текст: ~3 КБ
  * Метаданные: ~100 байт
  * **Итого**: ~3.1 КБ на ответ

**Расчёт:**

* 10 млн вопросов × 5.2 КБ ≈ **52 ГБ**
* Средний вопрос имеет 3 ответа: 30 млн ответов × 3.1 КБ ≈ **93 ГБ**
* С учётом индексов и overhead (×2): **~300 ГБ**

**Вывод**: Объём данных помещается на один сервер, но для масштабирования лучше использовать репликацию.

## Шаг 3: Высокоуровневая архитектура

### Компоненты системы

```
┌─────────────┐
│   Пользователь   │
└──────┬──────┘
       │
       ↓ HTTPS
┌─────────────┐
│  CDN / CloudFlare │ (статический контент, кэш)
└──────┬──────┘
       │
       ↓
┌─────────────┐
│ Load Balancer │ (Nginx / AWS ALB)
└──────┬──────┘
       │
       ↓
┌─────────────────┐
│  Web Servers     │ (Node.js / Python)
│  (API + SSR)     │ ──┐
└─────────────────┘   │
       │              │ (несколько инстансов)
       ↓              │
┌─────────────┐       │
│    Redis    │ ←─────┘ (кэш)
│  (кэширование) │
└─────────────┘
       │
       ↓
┌─────────────┐
│  PostgreSQL  │ (основная БД)
│  Master      │
└──────┬──────┘
       │
       ↓ (репликация)
┌─────────────┐
│  PostgreSQL  │ (read replicas)
│  Replicas    │
└─────────────┘
```

### Ключевые решения

**1. Почему PostgreSQL?**
* Структурированные данные (вопросы, ответы, комментарии)
* Сложные запросы (JOIN, сортировка, фильтрация)
* ACID-транзакции для целостности данных (см. [Типы баз данных](./database-types.md#acid))
* Полнотекстовый поиск (для будущего поиска по вопросам)

**2. Почему Redis?**
* Кэширование списка вопросов (часто запрашивается)
* Кэширование страниц вопросов (популярные вопросы)
* Снижение нагрузки на БД в 10-100 раз

**3. Почему SSR?**
* SEO-требования (поисковые системы должны видеть контент)
* Быстрый первый рендер (пользователь видит страницу сразу)

**4. Почему CDN?**
* Статические ресурсы (CSS, JS, изображения)
* Географическое распределение (быстрая доставка)

### Схема базы данных

```sql
-- Таблица вопросов
CREATE TABLE questions (
  id BIGSERIAL PRIMARY KEY,
  title VARCHAR(500) NOT NULL,
  body TEXT NOT NULL,
  author VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  views INT DEFAULT 0,
  answers_count INT DEFAULT 0,
  is_answered BOOLEAN DEFAULT FALSE
);

-- Индексы для быстрого поиска
CREATE INDEX idx_questions_created_at ON questions(created_at DESC);
CREATE INDEX idx_questions_answers_count ON questions(answers_count DESC);
CREATE INDEX idx_questions_is_answered ON questions(is_answered);

-- Таблица ответов
CREATE TABLE answers (
  id BIGSERIAL PRIMARY KEY,
  question_id BIGINT NOT NULL REFERENCES questions(id),
  body TEXT NOT NULL,
  author VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  votes INT DEFAULT 0,
  is_accepted BOOLEAN DEFAULT FALSE
);

-- Индексы
CREATE INDEX idx_answers_question_id ON answers(question_id);
CREATE INDEX idx_answers_is_accepted ON answers(is_accepted);

-- Таблица комментариев
CREATE TABLE comments (
  id BIGSERIAL PRIMARY KEY,
  question_id BIGINT REFERENCES questions(id),
  answer_id BIGINT REFERENCES answers(id),
  body TEXT NOT NULL,
  author VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);

-- Индексы
CREATE INDEX idx_comments_question_id ON comments(question_id);
CREATE INDEX idx_comments_answer_id ON comments(answer_id);
```

### Стратегия кэширования

**1. Кэширование списка вопросов**

```
Ключ: "questions:list:page:1:sort:popular"
Значение: JSON со списком вопросов
TTL: 5 минут
```

**Почему 5 минут?**
* Баланс между актуальностью и производительностью
* Новые вопросы появятся через 5 минут (приемлемо)

**2. Кэширование страницы вопроса**

```
Ключ: "question:123"
Значение: JSON с вопросом и ответами
TTL: 10 минут
```

**Почему 10 минут?**
* Популярные вопросы редко меняются
* Новые ответы появятся через 10 минут (приемлемо)

**3. Инвалидация кэша**

При создании нового ответа:
```python
# Псевдокод
def create_answer(question_id, body):
    # Сохранить ответ в БД
    answer = db.save_answer(question_id, body)
    
    # Инвалидировать кэш вопроса
    redis.delete(f"question:{question_id}")
    redis.delete(f"questions:list:*")  # Инвалидировать все списки
    
    return answer
```

### Оптимизация производительности

**1. Пагинация**

* Использовать `LIMIT` и `OFFSET` в SQL
* Для больших offset использовать курсорную пагинацию (по ID)

**2. Ленивая загрузка**

* Список вопросов загружается сразу
* Полный текст вопроса и ответы загружаются асинхронно (AJAX)

**3. Индексы БД**

* Индексы на часто используемых полях (created_at, answers_count)
* Составные индексы для сложных запросов

## Шаг 5: Масштабирование и надёжность

### Нужно ли шардирование?

**Анализ:**

* **Объём данных**: ~300 ГБ (помещается на один сервер)
* **Нагрузка**: 60 RPS (один сервер легко справляется)
* **Распределение**: 95% чтение, 5% запись

**Вывод**: **Шардирование НЕ нужно** на начальном этапе.

**Почему?**
* Один PostgreSQL-сервер может обработать тысячи RPS
* Объём данных помещается на один сервер
* Шардирование усложняет архитектуру без необходимости

**Когда понадобится шардирование?**
* Когда объём данных превысит 1-2 ТБ
* Когда нагрузка превысит 1000 RPS на запись
* Когда один сервер не справляется

### Репликация

**Архитектура:**

```
PostgreSQL Master (запись)
    │
    ├── Replica 1 (чтение)
    ├── Replica 2 (чтение)
    └── Replica 3 (чтение)
```

**Почему репликация?**

1. **Масштабирование чтения**
   * 95% запросов — чтение
   * Направляем SELECT на реплики
   * Master обрабатывает только записи

2. **Отказоустойчивость**
   * Если master падает → failover на реплику
   * Минимальный downtime

3. **Географическое распределение**
   * Реплики в разных регионах
   * Низкая latency для пользователей

**Настройка:**

* **Master**: принимает все INSERT/UPDATE/DELETE
* **Replicas**: принимают только SELECT
* **Load Balancer**: направляет запросы на реплики для чтения

### Отказоустойчивость

**1. Репликация БД**

* Автоматический failover при падении master
* Реплики синхронизируются асинхронно

**2. Множественные инстансы API**

* Несколько web-серверов за Load Balancer
* Если один падает — остальные продолжают работать

**3. Кэш (Redis)**

* Redis Cluster для отказоустойчивости
* Если Redis падает — запросы идут напрямую в БД (медленнее, но работает)

**4. Мониторинг и алерты**

* Мониторинг здоровья сервисов
* Алерты при падении компонентов

## Мониторинг

### Ключевые метрики

Подробнее: [Метрики и мониторинг](./metrics.md) (latency, p95, RPS, SLO, дашборды).

**1. Производительность**

* **Latency**: время отклика API (p50, p95, p99)
* **Throughput**: RPS (запросов в секунду)
* **Error rate**: процент ошибок

**2. Инфраструктура**

* **CPU, RAM, Disk**: использование ресурсов
* **Database connections**: количество подключений к БД
* **Cache hit rate**: процент попаданий в кэш

**3. Бизнес-метрики**

* Количество вопросов в день
* Количество ответов в день
* Популярные вопросы

### Инструменты

* **APM**: Datadog, New Relic, AppDynamics
* **Логи**: ELK Stack (Elasticsearch, Logstash, Kibana)
* **Метрики**: Prometheus + Grafana
* **Алерты**: PagerDuty, Opsgenie

### Дашборды

**1. Performance Dashboard**

* График latency (p50, p95, p99)
* График RPS
* График error rate

**2. Infrastructure Dashboard**

* CPU, RAM, Disk usage
* Database connections
* Cache hit rate

**3. Business Dashboard**

* Количество вопросов/ответов
* Популярные вопросы
* Активность пользователей

### Ключевые решения — итог

| Компонент | Решение | Обоснование |
|-----------|---------|-------------|
| **БД** | PostgreSQL | Структурированные данные, сложные запросы, ACID |
| **Кэш** | Redis | Быстрое кэширование списков и страниц |
| **Масштабирование** | Репликация (не шардирование) | 95% чтение, объём данных небольшой |
| **Архитектура** | Множественные инстансы API | Горизонтальное масштабирование, отказоустойчивость |
| **Рендеринг** | SSR | SEO-требования |
| **CDN** | CloudFlare / AWS CloudFront | Быстрая доставка статики |

   * Определить распределение чтение/запись

### ❌ Частые ошибки:

1. **Слишком сложная архитектура** — не нужно шардирование для 60 RPS
2. **Игнорирование кэширования** — кэш критичен для производительности
3. **Недооценка масштаба** — нужно рассчитать нагрузку и объём данных
4. **Отсутствие мониторинга** — мониторинг важен для production-систем
5. **Игнорирование отказоустойчивости** — реплики нужны даже для небольших систем
